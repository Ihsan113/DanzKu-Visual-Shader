# DanzKu Visual Shader V5.2.26 — Complete Source Bundle

Derived from the V5.2.24 source bundle. Includes native Zygisk source, KernelSU packaging files, config bridge, monitor Android project, validation script, and GitHub Actions workflow for the ARM64 native module and Monitor APK.

Visual Proof A/B: `visual_proof=1` enables telemetry. `visual_proof_bypass=0` is normal enhancement mode. Set `visual_proof_bypass=1` for a baseline pass that neutralizes visual enhancement uniforms while retaining the capture/reconstruction/output path.

Telemetry: visual_proof, visual_proof_bypass, visual_proof_frames, visual_proof_bypass_frames.

This bundle is source-complete. Native `.so` and APK are built by GitHub Actions.


## Resource / Performance Controls
- `ram_optimization=1`: releases the temporal history framebuffer/texture when temporal processing is disabled; it does not reduce active temporal visual quality.
- `fps_boost=1`: enables a low-overhead runtime mode by reducing config polling/report frequency; shader visual parameters are unchanged.

These controls are intentionally conservative: they reduce overhead without dynamically lowering reconstruction quality.

### New game visual controls
- Vibrance
- Anisotropic Visual Enhancement
- Frame Buffer Optimization
- Adaptive Texture Enhancement
- HDR Enhancement

All are disabled/neutral by default in the native shader except the conservative values in `visual.conf`; APK controls can adjust them live.

## APK Target App Manager

V5.2.26 now supports an APK-managed target package list.

- Target list: `module/config/targets.conf`
- One Android package per line.
- Monitor APK button: **TARGET APPS / PACKAGE LIST**
- The APK enumerates launchable installed apps and lets the user enable/disable DanzKu per package.
- Native Zygisk matching uses the base package before `:` so child processes are covered too.
- The per-app report/files directory is derived from the selected package.
- Target changes take effect after restarting the target app.
- Default targets in this build: Mobile Legends and Free Fire MAX.

Note: target selection only controls injection eligibility. The current native hook still expects a Unity/EGL path; selecting a non-Unity app such as YouTube does not by itself add video-surface support.

## V5.2.26 Media Engine YouTube profile
The supplied base now contains an opt-in media profile for `com.google.android.youtube`.

The media profile is deliberately separate from the game Visual Shader path. When active it uses only a lightweight framebuffer transform with:
- tone mapping
- highlight recovery
- shadow lift
- local contrast
- vibrance
- adaptive detail
- skin-tone protection

`media_engine=0` is the default. The engine only considers conservative near-16:9 EGL surfaces (minimum 720x400), so ordinary portrait/full-screen UI surfaces are skipped.

Important architectural boundary: the media engine does **not** hook Codec2, `GraphicBufferMapper::lockYCbCr`, BufferQueue, DRM, or protected decoder paths. The earlier YouTube investigation established that video frames are delivered through Codec2/GraphicBuffer YUV surfaces, but this source does not attempt to intercept or rewrite those protected/media-buffer paths. The implemented media engine therefore processes only an EGL framebuffer if YouTube actually presents a suitable frame through EGL.

This is an HDR10+-like visual transform, not true HDR10+ metadata generation.


## Media Engine path revision
The YouTube Media Engine now uses the discovered Codec2/BufferQueue stack as a
read-only identity gate before its EGL presentation transform. It intentionally
does not interpose `GraphicBufferMapper::lockYCbCr()`, `C2AllocationGralloc::map()`,
BufferQueue, DRM, or protected decoder memory. Runtime telemetry reports whether
the Codec2/BufferQueue stack is present and whether a conservative video-shaped
EGL surface has been observed. This is evidence/gating, not a claim that every
matching EGL surface is necessarily the decoded video frame.
