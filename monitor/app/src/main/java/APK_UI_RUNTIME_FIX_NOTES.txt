DanzKu Monitor APK UI/runtime status fix
- V9/V10/V11/V12/POCO tuning sliders now depend on their owning feature toggle and Visual Engine master.
- Runtime status now exposes feature flags, pipeline/output state, runtime-applied values, and config-only temporal/device values.
- Native shader code is unchanged.
- Stage 3 True Supersampling: added a toggle + two sliders (scale, max pixels)
  in the runtime page, following the exact same addSectionHeader/addToggle/
  addFloatControl pattern as every other feature. Scale/max-pixels sliders
  depend on the True Supersampling toggle via parentForControl(), same as
  e.g. aa_strength depends on advanced_aa. The native side now echoes
  true_supersampling/supersampling_scale/supersampling_max_pixels under
  those exact config-key names in the v40_runtime report (same convention
  as every other feature) and appends the full dz_ss diagnostic block
  (ss_state, ss_fallback_reason, ss_resolve_ok, ss_fn_*, etc.) so the
  existing single runtime-report file the Monitor already reads carries
  this feature's status too - no new file, no new root command needed.
  buildStatusText() surfaces this as its own "Stage 3 - True Supersampling
  status" block, and true_supersampling participates in pendingFeatures()
  the same way every other toggle does.
- v5.2.27: removed the "POCO M5 TUNING" section entirely (1 toggle + 5
  sliders) and the "Low-Memory History (half resolution)" toggle. Both
  were investigated first (traced to shader source) and ruled out as the
  cause of a reported crop/zoom - removed per explicit request anyway, not
  because they were found to be broken. Removed every reference in
  parentForControl(), runtimeFeatureKeys, runtimeValueKeys, configOnlyKeys,
  and pendingFeatures()'s key list; the addSectionHeader() page-routing
  check for "POCO M5" was also dropped since that section no longer exists.
  Version bumped 5.2.26 -> 5.2.27 (build.gradle + every "V5.2.26" status
  label) alongside the matching native module.prop bump, so an updated
  build is visibly distinguishable from the one that showed the bug.
- V5.3.0 runtime reader follow-up: process discovery now prefers `pidof <package>` and falls back to `ps`, then checks every returned PID for a matching v40 runtime report. The reader also retries through plain `su -c` when the mount-master shell returns an empty process view, and it checks the common `/data/user/0`, `/data/data`, and `/data/user_de/0` report paths. This is specifically intended to fix Android 13/KernelSU/Magisk cases where the target process is visible to root but the Monitor's previous `ps`/`su -mm` combination reported `PID FOUND: NO`. Native hook code is unchanged by this follow-up.
